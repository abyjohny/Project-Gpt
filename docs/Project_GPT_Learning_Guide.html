Phase 1: RAG From Scratch CHAPTER 00
Setup & Ollama — Running an AI on Your Own Laptop
📂 Primary Implementation: rag/ollama_client.py

What is a "model"?

When people say "ChatGPT" or "Qwen", they mean a model: one very large file full of numbers. Those numbers were learned by reading a huge amount of text.

A model has one skill: given some text, guess the next word. It does this extremely well, so well that it can explain, summarise, write code and hold conversations.

"The capital of France is"  →  model  →  "Paris"

That's it. Everything else (chatting, answering from documents, using tools) is built around this one skill.

What is Ollama?

Running a model yourself used to be complicated. Ollama makes it easy:

  • It downloads models for you (ollama pull qwen3.5:4b)
  • It runs them on your graphics card (GPU)
  • It opens a small local web address (http://localhost:11434) that any program can talk to
💡

💡 "localhost" means this computer. When our Python code talks to localhost:11434, the message never leaves your laptop.

⚠️ A real bug we hit: "localhost" made every request 2 seconds slower! Computers have two kinds of addresses: the old style (IPv4, like 127.0.0.1) and the new style (IPv6, like ::1). On Windows, the name "localhost" tries the new address first. Ollama only listens on the old one, so Windows knocked on the wrong door, waited ~2 seconds, then tried the right door.

Each question was taking ~2.1 s just to be turned into numbers. After we switched to http://127.0.0.1:11434 in rag/config.py, it took ~0.065 s, about 30× faster, with no other changes.

Lesson: if something is slow by a suspiciously round, constant amount (exactly ~2 s every time), it's usually a network timeout, not "the AI being slow".

Think of Ollama as a kitchen and the models as chefs. Our Python code is the waiter: it takes the order (your question) to the kitchen and brings back the dish (the answer).

The two models we use

Model Job Size Analogy
qwen3.5:4b Reads and writes answers ~3 GB The expert who answers questions
nomic-embed-text Turns text into meaning-numbers ~0.3 GB The librarian who files every page by topic

Why two? Because they do completely different jobs. The librarian is small and fast and organises your library. The expert is big and smart and writes the answers. You'll understand the librarian fully in note 4.

Why "4b" for your laptop?

Your laptop has an RTX 3050 with 6 GB of video memory (VRAM). The model has to fit in that memory to run fast.

Model size Memory needed (approx.) On your laptop
2b ~2 GB Very fast, but less smart
4b ~3.5 GB ✅ Best balance
9b ~6.5 GB Doesn't fully fit → part of it runs on the slower CPU
💡

💡 "Quantized": the downloaded models are compressed. Each number is stored with fewer digits (like rounding 3.14159265 to 3.14). The model gets much smaller and only very slightly less accurate. That's how a 4-billion-number model fits in about 3 GB.

How our code talks to Ollama

Open rag/ollama_client.py. It's just two web requests:

1. Embed (turn text into numbers)

POST http://localhost:11434/api/embed
{ "model": "nomic-embed-text", "input": ["hello world"] }

→ { "embeddings": [[0.012, -0.551, 0.309, ...]] }

2. Chat (get an answer)

POST http://localhost:11434/api/chat
{
  "model": "qwen3.5:4b",
  "messages": [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user",   "content": "What is RAG?"}
  ]
}

Roles in a chat: - system → the house rules ("always cite sources", "be concise") - user → what you typed - assistant → what the AI replied before (so it remembers the conversation)

💡

💡 The model has no memory between requests. To "remember" a conversation, we send the whole conversation again every time. ChatGPT works the same way.

🧪 Try it yourself

Open a terminal and run:

ollama list                      # which models you have
ollama run qwen3.5:4b            # chat directly in the terminal (type /bye to exit)

Ask it: "What did the NHCX document say about preauth cancellation?"

It will either say it doesn't know, or (worse) make something up. It has never seen your document. Keep that in mind; it's exactly the problem RAG solves.

Phase 1: RAG From Scratch CHAPTER 01
What is RAG? — The Open-Book Exam
📂 Primary Implementation: rag/config.py, ingest.py

The problem

Imagine a very smart friend who has read millions of books, but none of yours.

  • They don't know your company's NHCX integration document.
  • They don't know your ClaimLens code.
  • They stopped reading at some date, so they don't know anything newer.
  • And when they don't know something, they sometimes confidently make it up.

That friend is a language model like Qwen.

The obvious fix (that doesn't work)

"Just paste the whole document into the chat!"

A 200-page PDF is around 100,000+ words. The model's "desk" (its context window) is much smaller, and even when it fits: - it gets slow, - it gets confused (important details get lost in the middle), - and you'd have to paste it every single time.

The smart fix: RAG

RAG = Retrieval-Augmented Generation. Let's break the name down:

Word Meaning Analogy
Retrieval Find the few paragraphs that matter Open the textbook at the right page
Augmented Add those paragraphs to the question Put the page next to the exam paper
Generation The AI writes the answer from them Write the answer using the page

It's an open-book exam. The student (Qwen) is smart but doesn't know your book. So before each question, a librarian finds the right 5 pages and puts them on the desk. The student reads only those 5 pages and answers.

The two halves of RAG

Half A — Preparing the library (done once per document)

  Your files          📄 NHCX_spec.pdf   📝 notes.docx   💻 code.py
       │
  [1] LOAD            take the words out of each file
       │
  [2] CHUNK           cut the words into small pieces (a few paragraphs each)
       │
  [3] EMBED           turn each piece into "meaning numbers"
       │
  [4] STORE           save the pieces + numbers in a vector database

This is like a librarian reading every page of every book and writing an index card for each page saying what it's about.

👉 Code: ingest.py

Half B — Answering a question (every time you ask)

  "How do I cancel a preauth?"
       │
  [5] EMBED QUESTION  turn the question into meaning numbers too
       │
  [6] SEARCH          find the pieces whose numbers are closest
       │
  [7] BUILD PROMPT    "Using ONLY these pieces: ... answer: How do I cancel a preauth?"
       │
  [8] GENERATE        Qwen writes the answer and says which piece it used [1][2]

👉 Code: chat.py

Why this is so powerful

Without RAG With RAG
"I don't know your document" or makes things up Answers from your document
Can't tell you where the info came from Cites file and page
Must retrain the model to teach it new things (very expensive) Just drop a new PDF in the folder and run ingest.py
Your documents may go to a cloud company Everything stays on your laptop

The one sentence to remember

ℹ️

RAG doesn't make the AI smarter. It puts the right information in front of it.

That's also why, when answers are bad, the cause is usually wrong pages retrieved (steps 2–6), not a "dumb" model. We'll learn to debug that in note 8.

Phase 1: RAG From Scratch CHAPTER 02
Loading Documents — Getting the Words Out
📂 Primary Implementation: rag/loader.py

The idea

The AI can only read plain text. But your files are "boxes":

  • A PDF stores letters at exact positions on a page, plus fonts, images, lines…
  • A Word file (.docx) is actually a zip folder of XML files describing paragraphs and styles.
  • A .txt / .md / .py file is already plain text 🎉

The loader opens each box and takes out only the words.

 📄 NHCX_spec.pdf  ──►  loader  ──►  "Pre-authorization is a request sent by..."
                                      + { source: "NHCX_spec.pdf", page: 12 }

Metadata — remembering where text came from

Along with the text, we save a few labels called metadata:

Label Example Why we need it
source NHCX_spec.pdf So the AI can say which file
page 12 So the AI can say which page, and you can check it yourself
path D:\...\NHCX_spec.pdf So we can update a file later without duplicates
file_type pdf Useful for filtering later ("only search PDFs")

Without metadata, the AI could answer but never tell you where the answer came from. With it, you get answers like: "Send a cancel request with the preauth ID [NHCX_spec.pdf, page 12]".

How each file type is read

Open rag/loader.py:

File type Library What we do
.pdf PyMuPDF (fitz) One piece per page, so we know page numbers
.docx python-docx All paragraphs and tables (API docs are full of tables!)
.txt .md .py .js … plain Python Just read the file

Tables in Word are turned into lines like:

Field | Type | Required
preauth_id | string | yes

so the AI can still understand the rows.

⚠️ Things that can go wrong

Problem What you'll see Why
Scanned PDF (a photo of paper) "No text found. Skipped." There are no letters, only an image. It needs OCR (reading text from images), which we'll add later.
Weird spacing / broken words Chunks look messy PDFs store letters by position, not as sentences. Our chunker cleans up most of this.
Headers/footers on every page "Page 3 of 200 – Confidential" repeated Harmless mostly; we'll filter these in Phase 2.
💡

💡 Quick test for a PDF: open it and try to select text with your mouse. If you can select it, we can read it. If it selects like a picture, it's scanned.

🧪 Try it yourself

After installing, run this in the project folder (put one PDF in data/documents first):

.\.venv\Scripts\python.exe -c "from rag.loader import *; docs = load_file(find_files()[0]); print(len(docs), 'pages'); print(docs[0].metadata); print(docs[0].text[:500])"

Look at the output. That raw, slightly messy text is exactly what the rest of the pipeline works with.

Phase 1: RAG From Scratch CHAPTER 03
Chunking — Cutting Documents into Pieces
📂 Primary Implementation: rag/chunker.py

Why cut documents into pieces?

Imagine asking a librarian "How do I cancel a preauth?" and they hand you the whole 200-page manual. Technically correct… totally useless.

You want them to hand you the one paragraph that answers it.

To do that, the library must be organised by paragraph-sized pieces, not whole books. Those pieces are called chunks.

Reasons we chunk: 1. Precision: small pieces = we find the exact spot. 2. Fits the AI's desk: we can only give the AI a limited amount of text (its context window). 3. Better meaning-numbers: a chunk about one topic gets a clear meaning. A chunk mixing 10 topics gets a blurry "average" meaning that matches nothing well.

How big should a chunk be?

It's a balance, like slicing a cake:

Chunk size Good Bad
Too small (1 sentence) Very precise Loses context. "It must be sent within 24 hours." What is "it"? 🤷
Too big (5 pages) Lots of context Blurry meaning, wastes the AI's desk space, worse search
Just right (2–4 paragraphs) ✅ One idea with enough context —

Our setting: CHUNK_SIZE = 1000 characters (about 2–3 paragraphs, ~250 tokens).

The smart way to cut: "recursive" splitting

We don't cut blindly every 1000 letters. That would slice words and sentences in half. Instead we try to cut at natural borders, best first:

 1st try:  blank lines      "\n\n"   → between paragraphs   (best)
 2nd try:  line breaks      "\n"     → between lines
 3rd try:  sentence ends    ". "     → between sentences
 4th try:  spaces           " "      → between words
 5th try:  anywhere                  → last resort           (worst)

If a paragraph is small enough → keep it. If it's still too big → cut it with the next border on the list. And so on. Then small neighbouring pieces are glued back together until each chunk is close to 1000 characters.

Overlap — the safety net

What if the answer sits right on the border between two chunks?

chunk 1: "...The hospital must send a cancellation request"
chunk 2: "referencing the original preauth ID within 24 hours..."

Neither chunk has the full sentence! 😱

So each chunk repeats the last bit of the previous one:

 chunk 1: [ ======== text ======== | overlap ]
 chunk 2:                          [ overlap | ======== text ======== | overlap ]
 chunk 3:                                                             [ overlap | ==== ]

Our setting: CHUNK_OVERLAP = 150 characters, about one or two sentences.

We only repeat WHOLE sentences 🧱

Repeating half a sentence would be messy ("...the original preauth ID" — what about it?). So the code works like building with Lego bricks:

  1. First it breaks the text into sentence-sized bricks.
  2. Then it stacks bricks into a chunk until the chunk is nearly full (~1000 characters).
  3. When it starts the next chunk, it copies the last brick or two from the previous chunk (as many as fit into the 150-character overlap budget).
 chunk 1: [ S1 ][ S2 ][ S3 ][ S4 ]
 chunk 2:             [ S3 ][ S4 ][ S5 ][ S6 ][ S7 ]
                        ↑ repeated sentences = overlap
⚠️

⚠️ If a single sentence is longer than the overlap budget, it can't be repeated, so that border has no overlap. That's why the overlap should be at least as long as a typical sentence in your documents.

Chunk IDs — fingerprints

Every chunk gets an ID made from its file, page, position and text (using a "hash", a function that turns any text into a short, unique-looking code like a3f9c21e…).

Why? If you run ingest.py twice, the same chunk gets the same ID, so the database updates it instead of storing a duplicate.

Read the code

Open rag/chunker.py and find: - clean_text(): tidies messy PDF spacing - _split_recursive(): the "best border first" cutting (used twice: once for chunk-size pieces, once for sentence bricks) - split_text(): the 3 passes (pieces → sentence bricks → chunks) - _merge_with_overlap(): glues bricks and adds the overlap - chunk_documents(): copies the metadata (file, page) onto every chunk

🧪 Try it yourself

.\.venv\Scripts\python.exe playground\01_chunking_demo.py
  1. Look at where each chunk starts and ends. Find the repeated sentence(s): that's the overlap.
  2. Change CHUNK_SIZE = 300 to 150. Run again. What happens?
  3. Change it to 2000. How many chunks now?
  4. Set OVERLAP = 40. The overlap disappears. Why? (Hint: are any sentences shorter than 40 characters?)
  5. Set OVERLAP = 0. Can you find a thought that's now split across two chunks?
ℹ️

🎯 Key lesson: chunking quality decides search quality. Bad chunks → wrong pages found → bad answers, no matter how smart the AI is.

Phase 1: RAG From Scratch CHAPTER 04
Embeddings — Turning Meaning into Numbers
📂 Primary Implementation: rag/embedder.py

This is the most important idea in RAG. Take your time with it.

The problem with normal search

Normal search (Ctrl+F) looks for the same letters.

You search: cancel preauth The document says: "To revoke a pre-authorization, send…"

Ctrl+F finds nothing. Same meaning, different words. 😞

We need a search that understands meaning, not spelling.

The big idea: a map of meanings

Imagine a giant map where every sentence has a location, and sentences with similar meaning are placed close together:

                     🗺️  THE MAP OF MEANINGS

     "cancel preauth" •  • "revoke pre-authorization"
                        • "withdraw approval request"

                                              • "claim settled"
                                              • "payment released"

  • "my cat sleeps in the sun"
                                    • "PostgreSQL database"
                                    • "Redis cache"

A location on a normal map is 2 numbers: (latitude, longitude).

An embedding is the location of a sentence on the map of meanings. But meaning is far richer than 2 directions, so this map has 768 directions. So every chunk becomes a list of 768 numbers:

"revoke a pre-authorization"  →  [0.021, -0.443, 0.118, 0.902, ... 768 numbers]

You can't picture 768 directions (nobody can!). Just think of the 2-D map; the idea is the same.

💡

💡 Vector is just the maths word for "a list of numbers that points somewhere". Embedding = the vector that represents a piece of text. People use the two words interchangeably.

Who decides the numbers?

The embedding model (nomic-embed-text). It was trained on millions of sentence pairs to learn: "these two mean the same → put them close; these don't → put them far apart".

It's a separate, small model. It doesn't chat or write answers. It only places texts on the map. Think of it as the librarian who reads every page and files it in the right spot.

Measuring "closeness": cosine similarity

To compare two locations we check which direction they point. If two arrows point the same way → same meaning.

   same direction       somewhat apart        opposite / unrelated
        ↗ ↗                  ↗  →                    ↗   ↙
   similarity ≈ 1.0     similarity ≈ 0.5        similarity ≈ 0

This score is called cosine similarity: 1.0 = identical meaning, around 0 = unrelated.

The formula (you'll see it written out in playground/02_embeddings_demo.py):

similarity = (multiply matching numbers and add them up)
             ÷ (length of arrow A × length of arrow B)

⚠️ The golden rule

ℹ️

Documents and questions MUST use the SAME embedding model.

Each model draws its own map. Comparing a location from one map with a location on another map is meaningless, like comparing kilometres with miles. If you ever change EMBED_MODEL, you must re-ingest everything (python ingest.py --reset).

The little "prefixes"

You'll see this in rag/config.py:

EMBED_DOCUMENT_PREFIX = "search_document: "
EMBED_QUERY_PREFIX    = "search_query: "

nomic-embed-text was trained to work best when told what kind of text it's looking at: a stored document, or a search question. It's a small trick that improves results.

Phase 1: RAG From Scratch CHAPTER 05
The Vector Database — Storing and Finding Meaning
📂 Primary Implementation: rag/vector_store.py

What it is

After embedding, every chunk has a "location" (768 numbers). Now we need somewhere to keep them and quickly answer one question:

ℹ️

"Here's a location. Which stored chunks are closest to it?"

That's exactly what a vector database does.

Normal database (like PostgreSQL) Vector database (like ChromaDB)
WHERE claim_id = 'CLM-123' "closest in meaning to how do I cancel a preauth?"
Finds exact matches Finds similar matches
Answers "yes/no, it matches" Answers "here are the 5 closest, with scores"

What we store for every chunk

Think of each chunk as an index card in a library drawer:

┌──────────────────────────────────────────────────────┐
│ ID:        a3f9c21e7b...                (fingerprint) │
│ EMBEDDING: [0.021, -0.443, 0.118, ...]   (location)   │
│ TEXT:      "To cancel a preauth, the hospital..."     │
│ METADATA:  source=NHCX_spec.pdf, page=12, chunk=3     │
└──────────────────────────────────────────────────────┘
  • Embedding is used to find the card.
  • Text is what we give the AI to read.
  • Metadata is what we show you as the source.

Why ChromaDB?

  • It runs inside our Python program. No server to install or start.
  • It saves to a normal folder: data/vector_db/
  • It's simple, which makes it perfect for learning. (Later we may move to Qdrant or pgvector for bigger projects; the idea stays exactly the same.)

We also switched off Chroma's anonymous usage reporting (anonymized_telemetry=False), so nothing leaves your machine.

How does it search so fast?

Simple way: compare the question with every card. Fine for 1,000 cards. That's exactly what our tiny database in playground/03_tiny_vector_db.py does.

Clever way (what Chroma does): with millions of cards, checking each one is slow. So Chroma builds a shortcut network called HNSW. Think of it like this:

ℹ️

To find a house in a city, you don't knock on every door. You take the highway to the right area, then main roads to the right neighbourhood, then side streets to the right house.

HNSW builds "highways" and "side streets" between cards, so a search only visits a few hundred cards instead of millions. It's almost perfectly accurate and thousands of times faster.

Updating files without duplicates

When you change a document and run ingest.py again, we: 1. Delete all old cards from that file (delete_file) 2. Add the new cards (upsert = "insert, or update if the ID already exists")

So your library never has stale or duplicate pages.

Read the code

rag/vector_store.py: - get_collection(): opens (or creates) our "drawer", set to measure closeness with cosine - add_chunks(): saves cards - search(): finds the closest cards and converts Chroma's distance into similarity (1 − distance) - list_sources(): which files are in the library

Phase 1: RAG From Scratch CHAPTER 06
Retrieval — Finding the Right Pages
📂 Primary Implementation: rag/retriever.py

What happens when you ask a question

 You: "How do I cancel a preauth?"
          │
  [5] EMBED the question       → its location on the map of meanings
          │
  [6] SEARCH the vector DB     → the 5 closest chunks (TOP_K = 5)
          │
      FILTER weak matches      → drop anything below MIN_SIMILARITY (0.35)
          │
      ✅ the pages handed to the AI

This is the R in RAG. It is the most important step.

ℹ️

🎯 If retrieval brings the wrong pages, even the smartest AI gives a wrong answer. It's like giving a brilliant student the wrong chapter in an open-book exam.

The two retrieval knobs

TOP_K: how many chunks to fetch

TOP_K Effect
1–2 Very focused, but might miss part of the answer
4–6 ✅ Usually the sweet spot
10+ Catches more, but adds noise and fills the AI's desk; small models get confused

You can change it live in the chat: /k 8

MIN_SIMILARITY: the quality bar

Every chunk comes with a similarity score (0 to 1). If the best match for a question is only 0.20, the documents probably don't contain the answer.

So we throw away weak matches. And if nothing passes the bar, we don't even ask the AI. We just say "I couldn't find this in your documents."

That's an important anti-hallucination trick: no relevant pages → no chance to make things up.

💡

💡 Similarity scores are relative, not absolute. Different embedding models give different ranges. With nomic-embed-text, strong matches are often 0.6–0.8 and unrelated text below 0.35. Watch the scores with /debug and adjust MIN_SIMILARITY to your documents.

Seeing retrieval with your own eyes: /debug

In the chat, type /debug. Now before every answer you'll see a table:

Why each house rule exists

Rule Why
"Use ONLY the sources" Stops the AI mixing in things it half-remembers from training
"Cite [1], [2]" You can check every claim against the original page
"Say you couldn't find it" Gives the AI a polite way out instead of inventing an answer
"Point out disagreements" Useful when two versions of a document conflict
⚠️

⚠️ Small models (like 4b) follow rules most of the time, not always. That's why we also have code-level protection: if retrieval finds nothing, we don't call the AI at all.

Temperature — the creativity dial

TEMPERATURE = 0.2

When the AI picks its next word, it has many options with different chances.

  • Low (0–0.3): almost always picks the most likely word → factual, consistent ✅ for documents
  • High (0.8–1.0): sometimes picks less likely words → creative, varied ✅ for stories/brainstorming

For answering from documents, we want a strict, careful student, not a poet.

Streaming — the typing effect

Instead of waiting 10 seconds for the full answer, we ask Ollama to stream: it sends each word as soon as it's ready. That's why the answer "types itself" like ChatGPT. Same total time, but it feels much faster.

Memory for follow-up questions

The model forgets everything between requests. To allow follow-ups like "now make that a checklist", chat.py keeps the last 3 question/answer pairs and sends them again with each new question. /clear wipes that memory.

"Thinking" mode is off

Qwen3.5 can "think out loud" before answering (it writes hidden reasoning first). That helps with hard maths and logic, but it's slower and not needed for "read this page and answer". We switched it off with ENABLE_THINKING = False. Try turning it on later and compare!

Phase 2: Better Search CHAPTER 09
Keyword Search (BM25) — Smart Exact Matching
📂 Primary Implementation: rag/keyword_search.py
📂

Phase 2 · Lesson 1 · Code: rag/keyword_search.py · Demo: playground/04_keyword_vs_meaning.py

The problem we're fixing

In Phase 1, every search was a meaning search (embeddings). It's brilliant at this:

You ask It finds Why it works
"How do I withdraw a preauth?" "…to cancel a pre-authorization…" Different words, same meaning ✅

But try asking about an exact thing:

You ask What can go wrong
"What does error E-1047 mean?" It might return E-1046 or E-1042. To an embedding model these look almost identical: "some error code"
"Show me policy POL-77812" Numbers have almost no "meaning", so the meaning-numbers come out blurry
"What is ABHA?" Rare abbreviations the model never learned well

Embeddings capture the gist. Sometimes you need the exact word.

The old-school hero: keyword search

Think of the index at the back of a textbook:

appendicitis ........ 12, 48
ABHA ................ 3, 7, 22
E-1047 .............. 31

You don't read the whole book. You look up the word and jump to the page. That's exactly what keyword search does. It's called an inverted index (normal: page → words; inverted: word → pages).

But which page is BEST? Enter BM25

If your question has 5 words and 40 chunks contain at least one of them, which one wins? BM25 (a scoring recipe from the 1990s that still powers Elasticsearch) gives points using 3 common-sense rules:

Rule 1: Rare words are worth more (called IDF)

  • "the" appears in every chunk → worthless, tells you nothing
  • "E-1047" appears in one chunk → gold, that chunk is almost certainly the one

Like in a crowd: "a person with two eyes" doesn't help you find anyone, but "a person with a green hat" does.

Rule 2: Repeated words count more, up to a point (called TF)

A chunk that says "preauth" 4 times is probably more about preauth than one that says it once. But 20 times isn't 20× better, so the points level off (diminishing returns).

Rule 3: Short chunks get a small bonus

Finding "appendicitis" in a 3-line chunk is a stronger signal than finding it once in a 2-page chunk.

score(chunk) = sum over question words of:   rarity  x  repetition (levelled off)  x  shortness bonus

That's it. No AI, no GPU, just counting. It takes milliseconds.

How we cut text into "words" (tokenizing)

Before counting, every text is turned into a list of lowercase words:

"Send the Cancel-Request for E-1042"
   → ['send', 'cancel-request', 'cancel', 'request', 'e-1042', 'e', '1042']

Notice: - "the", "for" are dropped. These are stopwords, too common to help. - "Cancel-Request" is kept whole and split, so both "cancel request" and "cancel-request" match. - "E-1042" stays together, so codes match exactly.

Its weaknesses (why we don't use it alone)

Weakness Example
No idea about meaning "withdraw" ≠ "cancel" → zero points 😬
Word forms "cancelled" ≠ "cancel" (we don't do stemming, to keep it simple)
Spelling mistakes "preuath" matches nothing

So: keyword search is strong where meaning search is weak, and the other way round. The obvious idea is to use both. That's the next lesson: Hybrid search.

Read the code

Open rag/keyword_search.py: - tokenize(): text → words - BM25Index.__init__(): builds the "book index" (postings) and the rarity scores (idf) - BM25Index.search(): the 3 rules in about 10 lines - get_index(): builds the index from everything in ChromaDB, and rebuilds it when the chunk count changes

💡 The keyword index lives in memory and is rebuilt from ChromaDB when the chat starts. If you re-ingest an edited file while chat is open, type /reload.

Phase 2: Better Search CHAPTER 10
Hybrid Search — Combining Meaning & Keywords with RRF
📂 Primary Implementation: rag/retriever.py
📂

Phase 2 · Lesson 2 · Code: rag/retriever.py → reciprocal_rank_fusion()

The idea

You now have two detectives:

🕵️ Meaning detective (embeddings) 🔎 Keyword detective (BM25)
Understands paraphrases: "withdraw" ≈ "cancel" Spots exact codes, names, numbers: "E-1047"
Gets confused by codes and rare terms Clueless about synonyms

Hybrid search sends both detectives out on the same question, and each comes back with a ranked list of suspects (chunks). Then we merge the two lists into one.

  question
     │
     ├──► meaning search ──► [ C7, C2, C9, C4, ... ]   (20 candidates)
     │
     └──► keyword search ──► [ C2, C5, C7, C1, ... ]   (20 candidates)
                                     │
                              MERGE (RRF)
                                     │
                         [ C2, C7, C5, C9, ... ]

The tricky part: how do you merge two lists?

The two detectives use different scoring systems: - meaning similarity: 0.0 to 1.0 (e.g. 0.71) - BM25 keyword score: 0 to... anything (e.g. 14.8)

Adding 0.71 + 14.8 is like adding kilometres and kilograms. It makes no sense.

The trick: ignore the scores, use the positions

"1st place" means the same thing in both lists. So we only use the rank. This is called Reciprocal Rank Fusion (RRF), a fancy name for a simple rule:

ℹ️

Every chunk gets 1 ÷ (60 + its position) points from each list it appears in.

Position Points
1st 1/61 = 0.0164
2nd 1/62 = 0.0161
10th 1/70 = 0.0143
not in list 0

Example:

Chunk Meaning rank Keyword rank Total points
C2 2nd → 0.0161 1st → 0.0164 0.0325 🥇
C7 1st → 0.0164 3rd → 0.0159 0.0323 🥈
C5 — 2nd → 0.0161 0.0161
C9 3rd → 0.0159 — 0.0159

A chunk that both detectives liked rises to the top. That's exactly what we want.

ℹ️

🤔 Why 60? It comes from the research paper that introduced RRF. It stops the 1st place from completely dominating, so 1st and 2nd are close and agreement between lists matters more. It's RRF_K in config.py, and you rarely need to change it.

What you'll see in the chat

With --debug, the Found by column tells you which detective found each chunk:

#  Found by          Meaning  Keyword  ...
1  keyword+meaning   0.712    9.41         ← both agreed: strong candidate
2  keyword           -        12.03        ← only exact words matched (e.g. a code)
3  meaning           0.655    -            ← only the meaning matched (a paraphrase)

Settings (in rag/config.py)

Setting Default What it does
RETRIEVAL_MODE "hybrid" "vector", "keyword" or "hybrid"
CANDIDATES_PER_SEARCH 20 How many chunks each detective brings back
RRF_K 60 The "60" in the formula

Phase 2: Better Search CHAPTER 11
Re-ranking — The Careful Cross-Encoder Judge
📂 Primary Implementation: rag/reranker.py
📂

Phase 2 · Lesson 3 · Code: rag/reranker.py · Demo: playground/05_reranker_demo.py

Fast search is a bit "blurry"

Remember how meaning search works: 1. The question becomes a list of numbers. 2. Every chunk became a list of numbers (earlier, during ingest). 3. We compare the numbers.

The question and the chunk never actually meet. Each one is summarised separately into numbers, and we compare the summaries. That's why it's so fast (milliseconds for 100,000 chunks), but some detail gets lost.

Example where it goes wrong:

ℹ️

Q: "When can a preauth NOT be cancelled?"

Chunk Meaning search thinks
A: "A preauth can be cancelled at any time before…" 😍 0.82: same words, same topic!
B: "Once the final claim is submitted, the cancellation is blocked." 🙂 0.71

Chunk B is the real answer. The word "NOT" barely changes the meaning-numbers.

The re-ranker reads them together

A re-ranker (technically a cross-encoder) is a different kind of model. You give it the question and one chunk at the same time, and it reads them side by side, word by word, like a teacher marking an answer:

 [ When can a preauth NOT be cancelled? ] + [ Once the final claim is submitted, ... ]
                                │
                          re-ranker model
                                │
                          score: 0.94  ✅

Because it sees both texts together, it understands how they relate: negations ("not"), who did what, and whether the chunk actually answers the question or just mentions the same words.

Why not use the re-ranker for everything?

It's slow: it has to read every pair from scratch.

Meaning search Re-ranker
Reads question + chunk separately (pre-computed) together, every time
100,000 chunks ~20 ms ~hours 😅
30 chunks ~20 ms ~0.2–1 second ✅
Accuracy good excellent

So we use both, like a hiring process:

 all chunks ──[fast search: CV screening]──► ~30 shortlisted ──[re-ranker: interviews]──► best 5

This "retrieve, then re-rank" pattern is used by nearly every serious RAG system.

The model we use

BAAI/bge-reranker-v2-m3, a free, open model: - Downloaded once from Hugging Face (~2.2 GB), then runs fully offline - Runs on your GPU in 16-bit mode (~1.1 GB of VRAM), next to Qwen - Understands 100+ languages

It needs PyTorch (the engine that runs most AI models) and transformers (a library that knows how to load models from Hugging Face).

Scores and the safety filter

The re-ranker gives a score from 0 to 1:

Score Meaning
0.8 – 1.0 Directly answers the question
0.1 – 0.8 Related, partly useful
below 0.02 Not relevant, thrown away (MIN_RERANK_SCORE)

This makes "I could not find this in your documents" more reliable: junk chunks no longer reach Qwen.

...but don't keep only ONE chunk (RERANK_MIN_KEEP)

A real failure: "what is search api used for?". The document never says "search API". It says "Payer Discovery API" and "Policy Discovery API". The judge kept just 1 of 33 chunks (score 0.30). Qwen saw one view of the topic and answered only half of it.

So there is a safety net. If at least one chunk passes the filter (the question IS about your documents) but fewer than RERANK_MIN_KEEP = 3 do, the next-best chunks are kept anyway, up to 3.

  • If nothing passes, nothing is kept. "I could not find this" still works.
  • The order never changes, so the #1 chunk stays #1. Measured: Hit@1 and MRR on the exam were exactly the same.

Read the code

Open rag/reranker.py. The important part is score_pairs():

inputs = _tokenizer([[question, text] for text in batch], ...)   # glue question + chunk together
raw_scores = _model(**inputs).logits                             # model reads both, outputs a number
scores = torch.sigmoid(raw_scores)                               # squash into 0..1

That's the whole idea in 3 lines.

Phase 2: Better Search CHAPTER 12
OCR — Reading Scanned PDFs and Images
📂 Primary Implementation: rag/loader.py
📂

Phase 2 · Lesson 4 · Code: rag/ocr.py, rag/loader.py

Two kinds of PDF that look the same

Open two PDFs, and they can look identical on screen. Inside, they're completely different:

"Real" PDF (digital) Scanned PDF
Made by Word, a website, a billing system Made by a scanner or a phone camera
Stores actual letters: P r e a u t h Stores a photo of the page: millions of coloured dots
You can select and copy text Selecting text does nothing
Our loader copies the text instantly ✅ Our loader finds nothing ❌

Hospital discharge summaries, signed letters, old policy documents and ID cards are very often scanned. In Phase 1, those pages were simply skipped.

OCR = "look at the picture and type it out"

OCR stands for Optical Character Recognition. Like a person reading a photo of a letter and typing it out, the computer looks at the dots and works out which letters they form.

Classic OCR programs (like Tesseract) must be installed separately. But we already have something better on your computer: Qwen3.5 can see images (it's a vision model). So we just show it the picture and say: "Type out every word you see."

 scanned PDF page
       │  ① take a "photo" of the page (150 DPI picture)
       ▼
   PNG image
       │  ② send it to Qwen with the instruction "transcribe exactly"
       ▼
   plain text  ──►  chunk  ──►  embed  ──►  store   (same as any other page)

How does the loader know a page is scanned?

Simple test: it tries to copy the text first. If a page gives fewer than 30 real letters (OCR_MIN_TEXT_CHARS), it's probably a picture → OCR it.

So a mixed PDF (some typed pages, some scanned) works automatically: typed pages are copied (fast), and only the scanned pages are OCR'd (slow).

Image files (.png, .jpg, .jpeg, .webp) such as screenshots or photos of documents are always OCR'd.

OCR'd chunks get a label ocr: True in their metadata, so you can always tell their text was read, not copied.

Things to know ⚠️

Topic What to expect
Speed About 5–30 seconds per page. A 50-page scan can take 10+ minutes. Ingest it once, then it's saved.
Accuracy Very good on clean scans and tables; weaker on blurry photos and messy handwriting.
AI mistakes A vision AI can occasionally misread a number. For important numbers (amounts, IDs), check the original page. The citation tells you which page!
Quality vs speed OCR_DPI = 150 is a good balance. Try 200 for tiny text, 100 for speed.

Phase 2 · Lesson 5 · Code: evaluate.py

"It feels better" is not good enough

You change a setting, ask 2 questions, and the answers look better. 🎉 But did 5 other questions quietly get worse? You'd never know.

Professionals never tune by feel. They build a test set (an exam) and measure every change. That's what evaluate.py does.

What exactly do we measure?

We test retrieval, the "find the right page" step, because: 1. If retrieval is wrong, the answer is wrong, no matter how smart Qwen is. 2. It's fast to test: no waiting for Qwen to write answers. 3. It's objective: the right page either came back or it didn't.

The exam

A list of questions where we know which page holds the answer:

{ "question": "What is the waiting period for maternity cover?", "source": "policy.pdf", "page": 14 }

The scores

For every question we check: did the right page come back, and at what position?

Score Plain meaning Example
Hit@1 % of questions where the right page came 1st 70% = right page on top 7 times out of 10
Hit@5 % where the right page was anywhere in the top 5 90% = Qwen saw the answer 9 times out of 10
MRR Average of 1 ÷ position (1st → 1.0, 2nd → 0.5, 3rd → 0.33, missed → 0) 0.80 = usually 1st, sometimes 2nd

Higher is better for all three. Hit@5 is the most important for RAG: if the right page is in the top 5, Qwen can use it.

Where do the exam questions come from?

It picks 25 random chunks from your knowledge base and asks Qwen: "Write a question that this passage answers." We know which chunk (and page) each question came from, so we know the right answer automatically.

⚠️

⚠️ Watch out: AI-written questions often copy words from the passage, which makes keyword search look better than it really is. We ask Qwen to use its own words, but it doesn't always manage. Open data\eval\questions.json and fix or delete weird questions.

Option 2: Write your own (the gold standard)

Add your real questions to data\eval\questions.json:

Phase 3: Structure & Memory CHAPTER 14
Structure-Aware Chunking — Following Document Shape
📂 Primary Implementation: rag/chunker.py, rag/loader.py
📂

Code: rag/loader.py (Word/PDF → Markdown) · rag/chunker.py (split_structured) Settings: CHUNKING_STRATEGY, SECTION_CHUNK_SIZE, SECTION_MERGE_MAX, CHUNK_LOCATION, TABLE_COMPACT, TABLE_OVERLAP_ROWS

The problem with cutting by size

Phase 1 cut text every ~1000 characters at paragraph or sentence borders. Think of tearing pages out of a book at random:

  • One chunk can end in the middle of section 4.1 and continue into 4.2, mixing two topics.
  • A table row like | 3 | QUERIED | ... | ends up far away from its column names and its heading. On its own it means nothing.
  • The old Word loader even moved all tables to the end of the document, away from their headings.

The idea: first follow the structure, then cut by size

 Word / PDF ──► loader.py ──► Markdown with real headings and tables
                                 # Section 4: Workflow Codes
                                 ## 4.1 Provider-Side Codes
                                 | Code | Meaning |
                                 ...
               chunker.py ──► 1. split at headings      (one topic per chunk)
                              2. glue tiny siblings      (5.6.1 + 5.6.2 + 5.6.3)
                              3. cut big tables BETWEEN rows, repeat the column names
                              4. write the "address" on top of every chunk

A finished chunk looks like this:

Location: Section 4: Workflow Codes Reference > 4.1 Provider-Side Workflow Codes

| Code | Name | Meaning |
| 2 | QUERIED | Payer needs more information ... |
| 3 | REJECTED | ... |
  • Word files: headings come from the paragraph style ("Heading 1", "Heading 2"...), and tables stay in place.
  • PDFs: they have no real headings, so we guess them: a line whose font is 15% bigger than normal text (PDF_HEADING_SIZE_RATIO) counts as a heading. Tables come from PyMuPDF's find_tables(). A section that continues on the next page keeps its address.

⚠️ Lesson learned: the first version was WORSE

This is the most important part of this note. A "smarter" idea is not automatically better. Measure it. We ran the exam (evaluate.py) on two sets of 40 questions:

  • Exam A was written from the old chunks.
  • Exam B was written from the new chunks, with the address removed so the questions can't cheat.

Using both stops the exam from favouring one layout. Results with hybrid + re-rank:

Setup Exam A Hit@1 Exam B Hit@1 Overall Hit@1 MRR
Old loader + recursive 1000 (Phase 2) 85% 95% 90.0% 0.930
Structure, first try (1000 chars, no overlap) 78% 88% 82.5% 0.882
+ only nearest heading as address 78% 88% 82.5% ~0.88
+ 2000 chars 78% 90% 83.8% 0.892
+ 1200 chars, 1 overlap row 80% 90% 85.0% 0.898
Structure 1500, 1 overlap row, full address, compact tables 90% 92% 91.3% 0.931

Why was the first try worse? We compared the questions one by one. It came down to two things:

  1. No overlap in tables. Plain text repeats ~150 characters between chunks, but table pieces didn't. A row near a border lost its neighbours. Fixed with TABLE_OVERLAP_ROWS = 1.
  2. Chunks too small. Address line + column names + rows fill 1000 characters fast, which left too little real content per chunk. 1500 works best here: 1200 is too small and 2000 too big (one chunk then covers several topics again).

Also: compact tables (dropping the | --- | line) saves tokens and doesn't hurt quality.

Speed

Re-ranking takes about 0.7–1.3 s for 20–35 candidates on the RTX 3050, about the same for every layout. Earlier measurements of 3–30 s were other programs using the GPU at the same time, not the chunks. Always measure speed on a quiet machine, and check more than once.

Phase 3: Structure & Memory CHAPTER 15
Conversation Memory — Multi-Turn Dialogues
📂 Primary Implementation: rag/memory.py, chat.py
📂

Code: rag/memory.py · used by chat.py · tested by python evaluate.py followups

The problem

You: What payer response codes are there?
AI:  1 APPROVED, 2 QUERIED, 3 REJECTED ...
You: and what about the second one?

You know that "the second one" means QUERIED. Our search step doesn't, because it has no memory. It turns the words "and what about the second one?" into a meaning vector and looks for chunks that are similar to... nothing in particular. The wrong chunks come back, so you get a wrong answer.

Giving the chat history to the AI is not enough. The AI only reads the chunks the search found, and that search was run with the vague question.

Two ways to fix it

A. Glue on the previous question (free). Search with previous question + follow-up:

"What diagnosis type codes exist? What does the last one mean?"

This is ugly to read, but the re-ranker reads the whole thing and works out what is meant.

B. Query rewriting with Qwen (~1.5 s). Ask Qwen one extra, very small question:

ℹ️

"Here is the chat so far. Rewrite the last question so it makes sense on its own."

"and what about the second one?"  ──►  "What does payer response code 2 (QUERIED) mean?"

Both are wired up the same way:

  1. Search with the context-rich query, so the right chunks are found.
  2. Answer the original question, with the chat history included, so the reply sounds natural.
 question ──► [add context from memory] ──► search ──► re-rank ──► Qwen answers
                    ▲                                                 │
                    └──────────── memory (last N turns) ◄────────────┘

⚠️ Measured: the simple trick wins

python evaluate.py followups (8 conversations, hybrid + re-rank):

How the follow-up was searched Hit@1 Hit@5 MRR Extra time
no memory (as typed) 50% 75% 0.60 0
Qwen rewrite alone 62–75% 88–100% 0.75–0.88 ~1.2–1.7 s
previous question + follow-up 88% 100% 0.94 0
previous question + Qwen rewrite 88% 100% 0.94 ~1.5 s

Why is the clever Qwen rewrite worse? A 4-billion-parameter model sometimes picks the wrong item. Asked about "the queried one", it once wrote "...partially approved?". A wrong rewrite sends the search in the wrong direction. Gluing on the previous question can't make that mistake, because it never throws information away.

So the default is QUERY_REWRITE = "context". The Qwen modes still exist, and they also glue on the previous question so a bad rewrite does less harm. With a bigger chat model they may win. Measure again if you change models. (8 conversations is a small exam, so add your own!)

Three pieces in memory.py

Piece What it does
ConversationMemory Keeps the last MEMORY_TURNS question/answer pairs. Old answers are shortened (HISTORY_ANSWER_MAX_CHARS) so they don't push the sources out of the context window.
looks_like_follow_up() A free, instant guess (no AI): very short questions, questions that start with "and / what about / also...", or that contain pointing words ("it", "that", "second", "those").
prepare() Decides what to search for: the question as-is, previous question + follow-up (context), or previous question + Qwen rewrite (auto / always). Long chains are cut to the last 60 words.
rewrite() Calls Qwen with temperature=0 and at most 80 tokens. _clean_rewrite() throws away bad output (empty, or so long that Qwen started answering instead of rewriting). In that case we fall back to the original question.

Settings (rag/config.py)

Setting Meaning
MEMORY_TURNS = 3 How many earlier turns are remembered.
QUERY_REWRITE = "context" context = previous question + follow-up (free, default). auto = previous question + Qwen rewrite, for follow-ups only. always = the same for every question. off = no memory in the search (Phase 1/2).
HISTORY_ANSWER_MAX_CHARS = 1200 Old answers are cut to this length.

In chat.py you can change it live with /rewrite context|auto|always|off, look at the memory with /memory, and forget everything with /clear. When a question is rewritten, the chat shows searching for: … so you can see what was actually searched.

Measuring it

Strategy How the follow-up is searched
no memory exactly as typed
previous question + follow-up the context mode

"Didn't understand, can you clarify?" — a message with NO topic

A real chat that went wrong:

You: what is search api used for?
AI:  ...discovering payers [1]
You: didnt understand can you clarify..
AI:  I could not find anything relevant in your documents.     ← dead end!

What happened:

  1. looks_like_follow_up() said no. 5 words, no "and / what about", no "it / that".
  2. So we searched for "didnt understand can you clarify" on its own. Those words match nothing.
  3. The re-ranker (correctly!) threw every chunk away. With 0 chunks, Qwen is not even asked.

The message isn't a question about your documents. It's a question about the last answer. Searching again is the wrong move, so now there are three paths. They live in rag/pipeline.py, shared by chat.py, evaluate.py and the web UI:

message ──► is_clarification()?  (clarify words, and NO topic words)
               yes ─► re-use the last answer's sources    origin = "clarify"  (no search, instant)
               no  ─► prepare() ─► search ─► re-rank      origin = "search"
                                     │
                                     └─ found nothing, but it's a follow-up?
                                            ─► last answer's sources       origin = "fallback"
Piece What it does
is_clarification() True for "didn't get that", "can you clarify?", "explain it more simply", "give an example"... but only if no real topic words remain. "Can you clarify the claim deadline?" is a new question, so it is searched normally.
Turn.sources Memory now also remembers which chunks each answer used, so they can be re-used.
CLARIFY_HINT Tells Qwen: "the user didn't understand, explain again more simply, same sources, maybe an example".
fallback A follow-up that finds nothing gets the previous sources rather than a dead end. Qwen is still told to say "I could not find this" if they don't answer it.

The chat shows clarification -> re-using the sources of the previous answer when this happens.

previous question + follow-up 91% 100% 0.955

All 3 clarifications come out at #1 with origin "clarify", in 0.0 s, because there is no search. The same chat replayed: the second answer is now a step-by-step explanation with an example.

1. Streaming with Server-Sent Events (SSE)

A normal web request is "ask, wait, get everything at once". For an AI answer that means staring at nothing for 10 seconds. Instead, the response stays open and the server pushes small named messages as soon as they exist:

event: status
data: {"text": "Searching your documents..."}

event: token
data: {"text": "The deadline"}

Each message is event: + data: + an empty line. The browser reads the stream piece by piece (response.body.getReader() in app.js) and splits on the empty lines.

Why a worker thread? Search, re-ranking and Qwen are ordinary blocking Python. If they ran on the server's main loop, the whole server would freeze while one answer is being written: no stats, no uploads, nothing. So run_chat() runs in a thread and drops events into a queue, and the async side just forwards the queue to the browser.

Stop button: when you press Stop, the browser closes the connection. The server notices, sets a cancel flag, the worker breaks out of the token loop and closes the stream to Ollama. Qwen stops writing, so the GPU is free again straight away.

2. Citations you can click

The system prompt already makes Qwen write [1], [2][3] after facts (note 07). The UI turns those into chips:

  1. The answer's markdown is converted to HTML (marked) and sanitised (DOMPurify). Never put AI output into a page without sanitising it: a document could contain HTML or script tags.
  2. A tree walker finds [n] in the text (not inside code blocks) and replaces it with a button.
  3. Clicking it opens the source card and shows the exact chunk text the AI was given.

That last step is the real point of RAG: you can check the AI's homework.

3. Sessions: memory that survives a restart

chat.py forgets everything when you quit. rag/sessions.py saves every chat as a JSON file in data/sessions/, including the sources of every answer. When you reopen a chat, the ConversationMemory (note 15) is rebuilt from those messages, so follow-ups ("and the second one?") and clarifications ("didn't get it") still work after a restart.

rag/web_search.py works in four steps:

  1. Search DuckDuckGo (no API key) for the question, or the follow-up-aware search query.
  2. Read the top 3 pages in parallel (6-second timeout each, so a slow site can't freeze the chat). Search snippets alone are ~200 characters, too thin to answer from.
  3. Pick the paragraphs that share the most words with the question (BM25's tokenizer, note 09).
  4. Wrap them as SearchResult objects with type: "web", so the generator numbers and cites them exactly like document chunks.

Documents come first in the numbering and the prompt says they are the most trusted: your own spec beats a random blog post.

5. Live system stats

The System tab polls /api/stats every 2 seconds:

  • GPU memory / load / temperature come from nvidia-smi (ships with the NVIDIA driver).
  • Loaded models come from Ollama's /api/ps, which shows how much of Qwen is in VRAM.
  • Tokens per second come from Ollama itself: the last streamed message carries eval_count (tokens written) and eval_duration (nanoseconds). ollama_client.chat(stats=...) captures them.

6. Safer uploads

Uploading a file runs the same steps as python ingest.py <file>, plus a few guards a web endpoint needs:

  • Path(filename).name strips folders, so a file named ../../server.py can only land in data/documents.
  • Only SUPPORTED_EXTENSIONS are accepted, up to 200 MB.
  • If a file yields 0 chunks (blank, or a scan OCR couldn't read), you get an error instead of a fake "success".
  • After ingesting, the BM25 index is rebuilt. Re-ingesting an edited file can keep the same chunk count, and the index only auto-rebuilds when the count changes (note 09).

Agent Mode — Tool Use, Sandboxing & Step Execution
📂 Primary Implementation: rag/agent.py, rag/agent_tools.py

Chat and Cowork answer in one shot: search → write. Agent mode works in steps: the model picks a tool, we run it, it looks at the result, and decides what to do next.

The pieces

File Job

web/app.js Agent mode button, folder chips, live step timeline

How tool calling works (Ollama)

We send the tool descriptions as JSON schemas along with the messages:

{"type": "function", "function": {"name": "read_file",
  "parameters": {"type": "object", "properties": {"path": {"type": "string"}}}}}

The model replies either with normal text (the answer) or with:

{"role": "assistant", "tool_calls": [{"function": {"name": "read_file", "arguments": {"path": "server.py"}}}]}

We run the tool and append {"role": "tool", "content": "<result>"}, then ask again.

Tools (Phase 1 - all read-only)

Tool What it does

Safety rules

  1. Sandbox - every path is resolved (.., symlinks) and must be inside a folder you added in the UI (data/agent_folders.json). Whole drives (C:\) are refused.
  2. Read-only - no tool can write, delete or run commands (yet).
  3. Secrets - .env, *.pem, *.key, id_rsa* are never read.
  4. Limits - results are capped (6000 chars) and scans stop after 20 s, so one call cannot flood the small model's context window.

Small-model tricks

  • AGENT_CONTEXT_WINDOW = 16384 (bigger than Chat's 8192 - tool results pile up).
  • Old tool results are shortened; only the newest 3 stay complete.
  • The same call twice in a row gets a "you already have this" nudge instead of re-running.
  • Out of steps → tools are switched off and the model must answer with what it has.

"""

"""

import math
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent.parent))

from rag import config, ollama_client

SENTENCES = [
    "How do I cancel a pre-authorization?",              # 0
    "Steps to revoke a preauth request",                 # 1  same meaning as 0, different words
    "The claim was settled and payment released",        # 2  related topic (insurance), different meaning
    "My cat loves sleeping in the sun",                  # 3  totally unrelated
    "Procedure for withdrawing an approval request",     # 4  similar meaning to 0/1
]


def cosine_similarity(a: list[float], b: list[float]) -> float:
    """The formula behind "semantic search", written out by hand.

    dot product  = multiply matching numbers and add them all up
    length       = how long each arrow is
    similarity   = dot / (length_a * length_b)   -> between -1 and 1
    """
    dot = sum(x * y for x, y in zip(a, b))
    length_a = math.sqrt(sum(x * x for x in a))
    length_b = math.sqrt(sum(y * y for y in b))
    return dot / (length_a * length_b)


vectors = ollama_client.embed([config.EMBED_DOCUMENT_PREFIX + s for s in SENTENCES])

print(f"Each sentence became a list of {len(vectors[0])} numbers.")
print(f"First 8 numbers of sentence 0: {[round(x, 3) for x in vectors[0][:8]]} ...\n")

print("Similarity of every sentence to sentence 0:")
print(f'   "{SENTENCES[0]}"\n')
scores = sorted(
    ((cosine_similarity(vectors[0], vectors[i]), i) for i in range(1, len(SENTENCES))),
    reverse=True,
)
for score, i in scores:
    bar = "#" * int(score * 40)
    print(f"  {score:.3f}  {bar:<40}  {SENTENCES[i]}")

print("\nNotice: sentence 1 shares almost NO words with sentence 0, but scores highest.")
print("That is the power of embeddings: they compare MEANING, not spelling.")
print("\nTRY THIS: add your own sentences to SENTENCES and guess the scores before running.")

"""
Playground 03 - Build a tiny vector database in 30 lines.
========================================================

ChromaDB can feel like a black box. It isn't. At its heart, a vector DB does this:

    1. keep a list of (text, vector) pairs
    2. when a question comes in, turn it into a vector
    3. compare it with every stored vector
    4. return the closest ones

Run:   python playground/03_tiny_vector_db.py

(Real vector DBs add clever shortcuts so they don't have to compare with
EVERY vector when you have millions - but the idea is exactly this.)
"""

import sys
from pathlib import Path

import numpy as np

sys.path.insert(0, str(Path(__file__).resolve().parent.parent))

from rag import config, ollama_client


class TinyVectorDB:
    def __init__(self):
        self.texts: list[str] = []
        self.vectors: list[np.ndarray] = []

    def add(self, texts: list[str]) -> None:
        embeddings = ollama_client.embed([config.EMBED_DOCUMENT_PREFIX + t for t in texts])
        for text, vec in zip(texts, embeddings):
            self.texts.append(text)
            v = np.array(vec)
            self.vectors.append(v / np.linalg.norm(v))   # normalise: make every arrow length 1

    def search(self, question: str, top_k: int = 3) -> list[tuple[float, str]]:
        q = np.array(ollama_client.embed([config.EMBED_QUERY_PREFIX + question])[0])
        q = q / np.linalg.norm(q)
        # With length-1 arrows, cosine similarity is just the dot product.
        scores = np.array(self.vectors) @ q
        best = np.argsort(scores)[::-1][:top_k]          # indexes of the highest scores
        return [(float(scores[i]), self.texts[i]) for i in best]


db = TinyVectorDB()
db.add([
    "ABHA is a 14-digit health ID number issued under the Ayushman Bharat Digital Mission.",
    "A preauth can be cancelled by sending a cancellation request with the original preauth ID.",
    "PostgreSQL is an open-source relational database.",
    "Claims are settled after the insurer verifies the final bill and discharge summary.",
    "Redis is an in-memory key-value store often used for caching.",
    "Consent artefacts let patients control who can see their health records.",
])

for question in [
    "how to withdraw a pre authorization?",
    "what is the health id number?",
    "which tool is good for caching?",
]:
    print(f"\nQ: {question}")
    for score, text in db.search(question):
        print(f"   {score:.3f}  {text}")
